## 一、总体评价

两条链路的工程底子是好的：

- **权限第一道闸统一**：所有读写都先过 `requireOwner()`，未登录直接拒绝，`owner_id` 全程跟随登录身份（`api.ts` 30+ 处一致）。
- **企微服务端对「不可靠的外部回调」处理得当**：先回 `success` 再异步处理（5 秒约束）、`msgid` 去重先标记后处理（并发回调不会重复回复）、游标持久化、发送失败不推进游标（可安全重试）、加解密有 13 项本地全链路自测。
- **知识库导入对浏览器能力做了完整降级**：File System Access API → `webkitdirectory` 输入框，解析库全部动态导入不影响首屏，失败逐条记录不中断整批。
- **诚实的界面文案**：企微私域能力清单明确区分「已支持 ✅ / 规划中 🔜」，没有把蓝图写成已完成。

以下按严重度列出发现的问题。

## 二、发现并已修复的问题（本次提交）

### 🔴 P1-1 · AI 兜底是死代码（企微服务端）

- **位置**：`wecom-kf-service/src/rules.mjs` + `src/server.mjs`
- **问题**：原顺序是 `matchRule()`（关键词 **→ 默认兜底**）→ 只有 `!rule` 才问 AI。但 `matchRule` 未命中时总会返回默认规则，`rule` 永远非空 → **`aiFallback` 只要配了默认规则就永远不执行**，文档里「规则未命中时用 AI 判断意图」是假的。
- **修复**：拆出 `matchKeywordRule()` / `matchDefaultRule()`，服务端顺序改为 **关键词 → AI → 默认兜底**；`matchRule()` 保留原语义（关键词 ?? 默认）供既有调用与测试使用。
- **验证**：新增自测「AI 兜底先于默认规则」（stub DeepSeek 返回规则 id `demo`，断言回复是体验引导话术而非默认话术）→ 15/15 通过。

### 🟠 P2-1 · 管理密钥出现在 URL 查询串里

- **位置**：`wecom-kf-service/src/server.mjs`（`/api/sync`、`/admin/rules`）、`Console.tsx`（同步请求）
- **问题**：`?secret=xxx` 会落进浏览器历史、网关/Nginx 访问日志、前端错误上报的 URL 字段；且用普通字符串相等比较密钥（时序侧信道）。
- **修复**：服务端优先读 `x-admin-secret` 请求头，`?secret=` 兼容保留（旧文档/脚本不断）；比较改为 `crypto.timingSafeEqual`（等长才比）；CORS `Allow-Headers` 加 `x-admin-secret`；控制台同步改为只发头、URL 只留 `since`；README 更新调用示例。
- **验证**：新增自测「请求头鉴权（兼容 query）」：header 正确 200 / header 错误 403 / query 正确 200 → 通过。
- **注意**：已部署的旧前端仍用 query，服务端向后兼容，可安全灰度。

### 🟠 P2-2 · 企微同步覆盖人工编辑的「最新需求」

- **位置**：`cloud/api.ts:upsertLeadByExternalId`、`Console.tsx:syncKfCustomers`
- **问题**：`/api/sync` 每次都返回**全量客户档案**，原逻辑对每个有 `lastText` 的客户都 `update({need})` → 销售手工补写的需求，会在下一次同步时被企微侧的旧 `lastText` 静默冲掉（数据丢失且无提示）。
- **修复**：`upsertLeadByExternalId(customer, { touchNeed })`；控制台用本次 `payload.events` 里的 `externalUserId` 集合判断「谁真的来了新消息」，只有活跃客户才覆盖 `need`。新建线索仍用 `lastText` 初始化。
- **验证**：tsc + build 通过；**待实测**（需云端）。

### 🟡 P3-1 · 知识库重复导入会翻倍

- **位置**：`cloud/kb-import.ts:importItems / importFromFileMap`、`cloud/api.ts`
- **问题**：同一次文件夹「重新扫描 → 导入」会再插一遍，资料数翻倍、任务上下文被重复内容占满。
- **修复**：导入前用一次 `loadKnowledgeSourceIndex()`（`select id,source`，500 条，跳过 `source="手动录入"` 这种非唯一值）建 `来源路径 → 文档 id` 索引；同源文件走 `updateKnowledgeDoc()` 覆盖正文与 `chunks`；`ImportOutcome` 增加 `updated` 计数，界面显示「新增 X · 更新 Y」。索引查询失败时退回旧行为（宁可重复也不中断导入）。
- **验证**：tsc + build 通过；**待实测**（需云端）。

### 🟡 P3-2 · 知识检索只看「最新 30 份」

- **位置**：`cloud/api.ts:loadKnowledgeContext`
- **问题**：文件夹批量导入一次就能加几十上百份，第 31 份之后的资料**无论多相关都进不了任务上下文**。
- **修复**：上限放宽到 100 份；单份 1600 字、总预算 6000 字的截断不变，提示词体积可控。
- **说明**：更彻底的解法是「元数据粗排 → 精取正文」两段式或向量检索，列入路线图 P1-4。

### 🟡 P3-3 · `sync_msg` 不消费 `has_more`

- **位置**：`wecom-kf-service/src/server.mjs:handleKfEvent`
- **问题**：单次 `sync_msg` 上限 1000 条，原代码拉一批就结束；若积压超过 1000 条，剩余消息要等下一次回调才会被处理。
- **修复**：改为 `for(;;)` 循环，`has_more=1` 继续拉；每批处理完推进游标（中途抛错不推进，配合 `msgid` 去重可安全重试）；`next_cursor` 不变时强制退出防死循环。
- **验证**：15/15 自测通过（mock 返回 `has_more=0`，单批路径不变）。

### 🟡 P3-4 · 密钥与客户数据可能被误提交

- **位置**：根 `.gitignore`
- **问题**：`wecom-kf-service/config.json`（corpid / Secret / AESKey / DeepSeek Key）与 `data/`（`customers.json` 客户档案、`events.json` 对话、`state.json` 游标）**原本都不在忽略列表**，一次 `git add .` 就会把生产密钥和客户隐私推进仓库。
- **修复**：两条规则已加，`git check-ignore` 确认命中。
- **建议**：已在历史中提交过的密钥需在企微后台轮换（本仓库初始提交里未发现 config.json，当前无需轮换）。

### 🟢 P3-5 · lint 8 个 error 清零

- 7 个 `react-refresh/only-export-components`（shadcn/ui 惯例的 `export { Button, buttonVariants }`）→ `eslint.config.js` 对 `src/components/ui/**` 关闭该规则并写明理由；
- 1 个真问题：`ui/sidebar.tsx` 骨架条在 `useMemo` 里调 `Math.random`（重渲染宽度会跳）→ 改为固定宽度的纯计算。
- 验证：`npm run lint` 0 error / 0 warning；`npm run build` 通过。

## 四、架构上值得保留的设计（审查中确认有效）

1. **跟进记录复用 `messages` 表**（`role="follow_up"`、`task_id=线索 id`）——规避了受限账号建表被云端拦截的问题，且与普通会话消息天然隔离。
2. **企微对话按 `seq` 幂等导入**——游标重拉、清空浏览器存储重同步都不会产生重复记录。
3. **服务端只存企微侧事实，落库由登录态前端完成**——绕开了「服务端没有用户 session、只能写 `owner_id='anon'`」的限制，同时保住多租户隔离。
4. **知识库文件夹句柄存 IndexedDB**——下次「重新扫描」免重复授权，解绑即忘。
5. **`renderTemplate` 对未命名客户用「你」而非空值**——话术里不会出现裸 `{{name}}`。
